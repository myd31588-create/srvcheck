# 服务器体检仪 —— 作品集项目方案

> 定位一句话：一条命令，把任意云服务器"体检"一遍，生成一份**老板能看懂的中文诊断报告**。
> 它既是作品集，也是获客工具：免费帮企业跑一次体检，报告本身就在替你卖后续服务。

---

## 一、为什么这个作品有辨识度

市面上的同类工具（Lynis、OpenSCAP 等）是给运维工程师看的：英文输出、满屏技术术语、没有结论。
你这个产品的差异化恰恰在**输出的接收者**：

| 维度 | Lynis 等开源工具 | 服务器体检仪 |
|------|-----------------|-------------|
| 目标用户 | 运维工程师 | 小公司老板 / 非技术负责人 |
| 输出语言 | 英文 + 术语 | 中文 + 打分 + 风险等级 |
| 结论形式 | 100 行明细 | "75 分，有 2 个高危问题，修复约 ¥X" |
| 后续动作 | 无 | 报告尾部带服务入口（你的联系方式/托管套餐） |
| 使用方式 | 需要安装、配置 | 一条命令，无依赖，跑完即走 |

**一句话卖点**：老板不需要懂技术，只需要知道"我的服务器是健康的还是危险的、要花多少钱解决"。

## 二、核心功能设计

### 2.1 使用形态（务必极简）

```bash
# 在目标服务器上一条命令运行（MVP 阶段：java -jar 直接跑）
java -jar srvcheck.jar --html report.html
```

- 无需安装、不改系统配置、只读探测（体检仪绝不动客户的机器，这是信任底线）
- 跑完输出：终端摘要（评分 + TOP 3 风险）+ 单文件 HTML 报告
- 单文件 HTML 意味着可以直接微信发给老板，离线可看

### 2.2 检查项清单（MVP 目标 20+ 项，按类分组）

**系统健康（约 6 项）**
- CPU / 内存 / 磁盘水位（>80% 预警，>90% 高危）
- 系统运行时长与最近重启时间（频繁重启 = 不稳定信号）
- Swap 配置与使用情况
- 负载均值 vs 核数
- OOM Kill 记录（dmesg / journalctl）
- 僵尸进程数量

**安全配置（约 8 项，这是最能吓醒老板的部分）**
- SSH 是否允许 root 直接登录
- SSH 是否允许密码登录（建议密钥）
- SSH 是否改了默认端口 22
- 防火墙（firewalld/iptables/ufw）是否启用
- fail2ban 是否安装启用
- 对外开放端口清单（高危端口识别：3306/6379/8080 对公网开放 → 高危）
- /etc/passwd 中可疑账户、空密码账户
- sudo 权限配置是否放任

**数据安全（约 5 项，这是老板最痛的部分）**
- MySQL / Redis 是否监听公网（0.0.0.0）
- Redis 是否设置密码（未设密码 + 公网 = 已被挖矿团伙盯上）
- 数据库默认口令（尝试常见弱口令，仅提示不暴力破解）
- 是否存在 crontab 数据库备份任务
- 备份文件新鲜度（最近一次备份距今天数；"从来没有备份"标红加粗）

**网站与证书（约 4 项）**
- SSL 证书剩余有效期（<14 天预警）
- TLS 版本（1.0/1.1 → 高危）
- HTTP 安全响应头（HSTS、X-Frame-Options 等）
- 网站 HTTP 状态与响应时间

### 2.3 评分体系

- 总分 100：系统健康 30 + 安全配置 40 + 数据安全 20 + 网站证书 10
- 每项检查有权重和风险等级：✅ 正常 / ⚠️ 建议整改 / 🔴 高危
- 存在任何 🔴 项时，报告头部给出醒目结论，例如：
  > **您的服务器存在 3 个高危问题，其中"数据库可被公网直接访问"可能导致数据泄露或被勒索，建议 7 日内处理。预计修复费用：¥800-1500。**

### 2.4 报告设计（HTML 单文件）

结构（自上而下）：
1. **体检总评卡**：大字评分 + 风险计数 + 一句话结论（给老板看的）
2. **风险雷达/分类条形图**：四类得分可视化（纯 CSS/SVG，不引外部 JS 库，保证离线可看）
3. **高危问题详情**：每个高危项 = 问题是什么（大白话）+ 会导致什么后果 + 修复难度/费用区间
4. **完整检查明细**（可折叠，给技术人看，体现专业度）
5. **服务入口**：可配置的联系方式 + 服务套餐（维修、月度托管）——这是获客钩子，也是"作品"与"生意"的连接点

报告文案原则：**每一条风险都翻译成"钱和后果"**。"Redis 未设密码" → "攻击者可在几分钟内清空或加密你的业务数据"。

## 三、技术选型（顺便展示你的运维功力）

| 组件 | 选型 | 理由 |
|------|------|------|
| 语言 | Java 17 | 你的本命栈，作品集要展示主业能力 |
| 框架 | Spring Boot 3（仅用 CLI 部分，甚至可去掉） | 项目轻量，避免"体检仪还拖着个 Web 容器"的槽点 |
| 打包 | GraalVM Native Image 编译为**单二进制** | 亮点：客户机器无需装 JDK，一条命令即跑，体现运维素质（可作 P2 优化） |
| 探测方式 | 纯本机只读命令 + /proc + JNA | 不装 agent、不驻留进程 |
| 报告 | 手写单文件 HTML 模板（内联 CSS/SVG） | 零依赖、微信可发、离线可看 |
| 配置 | 单个 YAML（服务入口联系方式、检查项开关） | 方便给不同客户定制报告尾部 |

加分设计（面试/谈客户时的谈资）：
- 提供 `--json` 输出，方便接自动化流水线
- 自身代码里演示规范的日志、退出码、幂等性——"工具类产品的工程质量"也是作品的一部分

## 四、两周执行计划

### 第 1 周：骨架 + 核心检查项
- Day 1-2：项目骨架、检查项抽象（Check 接口：`run() -> Result`）、命令行入口
- Day 3-4：实现系统健康 6 项 + 安全配置 8 项
- Day 5：HTML 报告模板初版（总评卡 + 明细列表）
- 周末：在一台 99 元/年的轻量云服务器上实测，故意"弄坏"它（开公网 Redis、关防火墙）验证检测准确

### 第 2 周：数据安全项 + 报告打磨 + 演示素材
- Day 8-9：数据安全 5 项 + 网站证书 4 项
- Day 10：评分体系 + 风险等级配色 + 报告文案"翻译成钱"
- Day 11-12：报告美化（这是给老板看的东西，颜值就是转化率）、服务入口可配置化
- Day 13：录 3 分钟演示视频（场景化开头："这家公司服务器被黑了三个月没人发现——如果早花 1 分钟跑个体检……"）
- Day 14：写一篇配套文章《我写了个工具，专门体检小公司服务器》，发技术社区 + 公众号

### 验收标准
- ✅ 在 3 台不同配置的 Linux 服务器上跑通（Ubuntu / CentOS 各一）
- ✅ 报告能发给一个完全不懂技术的朋友，TA 能看懂自己的服务器有什么问题
- ✅ 演示视频里有一条完整链路：一条命令 → 60 秒 → 微信转发报告

## 风险与边界（务必遵守）

- 体检仪只做**只读探测**，绝不修改客户系统；弱口令检查只做"常见 3-5 个口令"的提示性验证并明确告知，不做暴力破解
- 报告数据不出客户服务器（本地生成 HTML），打消"你这工具会不会偷我数据"的顾虑——这也是卖点
- 免费体检前明确告知范围，避免被当成"黑客工具"误解
